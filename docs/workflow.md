# 運用手順

## 1. 対象を定める

[導入設定](project-profile.md)に、誰のどの業務を何のために整理するかを記録します。判断基準集や観察の着眼点も対象にできます。すべてを手順フローにする必要はありません。

専門家レビュー担当と利用承認担当を明示します。役割が不明な回答は通常の回答として記録でき、承認としては扱いません。

## 2. 原本を保存し、位置と版を固定する

既存のメモ・録音・PDF等は原本のまま `source/records/` へ保存します。録音から文字起こしした場合は、録音を残し、文字起こしを別ファイルに保存して対応する時刻を索引へ記録します。聞き取れない部分を推測で補いません。

新規の聞き取りには [対話・観察記録](../templates/source-record.md) を利用できます。記録した原文と、記録者の解釈を区別します。解釈は専門家の発言として登録しません。

`source/index.md` にSRC-ID、原本パス、位置、話者・記録者、資料種別を登録します。訂正には新しいSRC-IDを発行し、対象の旧SRC-IDを記します。複数の資料が矛盾するときは両方を保持し、どちらを採用するかをQにします。

原本をGitへコミットした後、その完全なコミットIDとSHA-256を索引へ記録します。索引が自身のコミットを参照する必要はありません。未コミットの場合は明示して草稿として扱い、履歴のないコミットを捏造しません。

## 3. 正本と確認事項を作る

[構造化Skill](../.agents/skills/structure-knowledge/SKILL.md)を用い、[正本テンプレート](../templates/canonical.md)から根拠のある項目だけを作ります。対象範囲、判断条件、否定側の分岐、例外、理由などは資料に明示されている範囲だけ記載します。

「資料に並んでいる順」と「業務で実行する順」は区別します。つながりが不明なら、項目を独立して残し、Qへ記録します。未知の遷移を終了・中止・次工程として作らないでください。

## 4. 回答・専門家確認・利用承認を反映する

質問への回答は原文として別資料へ保存し、SRC-IDを割り当てます。Qには回答の出所と反映先を記録し、部分回答なら残る質問を明示します。

[レビューSkill](../.agents/skills/review-knowledge/SKILL.md)と[記録テンプレート](../templates/review-record.md)を用い、対象版とIDを特定します。Qのclosed、専門家確認、利用承認はそれぞれ別の判断です。承認の対象用途も記録します。

内容変更のある項目・関係と、その変更に依存する項目を再確認します。旧版の確認を新版へ自動的に引き継がず、旧記録は履歴として保持します。

## 5. 派生物を作り、検査して保存する

[派生生成Skill](../.agents/skills/derive-knowledge-artifacts/SKILL.md)を使います。レビュー用の図には未レビューであることを表示します。正式指示として扱う場合は、項目・経路・文書・利用範囲の承認を確認します。

文書ID・版・対象ID・生成方法・入力ハッシュを[派生物管理票](../templates/artifact-record.md)へ記録します。正本と派生物を同時にコミットするときは、自分自身のコミットIDを書き込もうとせず、生成時の基準コミットと入力SHA-256で特定します。その後、実践記録から利用時点の正本コミットを参照します。

[検証チェックリスト](validation-checklist.md)を実施し、[検証記録](../templates/validation-report.md)へ結果を保存します。検証成功は専門家確認や利用承認ではありません。

## 6. 実践で得た知見を戻す

実践記録には、参照した正本の文書ID・版・コミット、事実、観察、担当者の仮説を区別して記録します。知識改善の候補をQにし、新しい根拠資料と専門家レビューを経て正本へ反映します。レポートから正本を自動更新しません。
